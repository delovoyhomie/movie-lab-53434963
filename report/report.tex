\section*{Текст задания}

Реализовать информационную систему, которая позволяет взаимодействовать с объектами класса Movie, описание которого приведено ниже:


\lstinputlisting[language=Java,basicstyle=\ttfamily\footnotesize,numbers=none]{model-spec.java}


Разработанная система должна удовлетворять следующим требованиям:


\begin{itemize}[leftmargin=*]

\item Основное назначение информационной системы - управление объектами, созданными на основе заданного в варианте класса.

\item Необходимо, чтобы с помощью системы можно было выполнить следующие операции с объектами: создание нового объекта, получение информации об объекте по ИД, обновление объекта (модификация его атрибутов), удаление объекта. Операции должны осуществляться в отдельных окнах (интерфейсах) приложения. При получении информации об объекте класса должна также выводиться информация о связанных с ним объектах.

\item При создании объекта класса необходимо дать пользователю возможность связать новый объект с объектами вспомогательных классов, которые могут быть связаны с созданным объектом и уже есть в системе.

\item Выполнение операций по управлению объектами должно осуществляться на серверной части (не на клиенте), изменения должны синхронизироваться с базой данных.

\item На главном экране системы должен выводиться список текущих объетов в виде таблицы (каждый атрибут объекта - отдельная колонка в таблице). При отображении таблицы должна использоваться пагинация (если все объекты не помещаются на одном экране).

\item Нужно обеспечить возможность фильтровать/сортировать строки таблицы, которые показывают объекты (по значениям любой из строковых колонок). Фильтрация элементов должна производиться по неполному совпадению.

\item Переход к обновлению (модификации) объекта должен быть возможен из таблицы с общим списком объектов и из области с визуализацией объекта (при ее реализации).

\item При добавлении/удалении/изменении объекта, он должен автоматически появиться/исчезнуть/измениться в интерфейсах у других пользователей, авторизованных в системе.

\item Если при удалении объекта с ним связан другой объект, связанные объекты должны удаляться.

\item Пользователи должны иметь возможность просмотра всех объектов. Для модификации объекта должно открываться отдельное диалоговое окно. При вводе некорректных значений в поля объекта должны появляться информативные сообщения о соответствующих ошибках.

\end{itemize}

В системе должен быть реализован отдельный пользовательский интерфейс для выполнения специальных операций над объектами:


\begin{itemize}[leftmargin=*]

\item Удалить один (любой) объект, значение поля tagline которого эквивалентно заданному.

\item Вернуть массив объектов, значение поля tagline которых содержит заданную подстроку.

\item Вернуть массив объектов, значение поля genre которых меньше заданного.

\item Получить список сценаристов, ни один фильм которых не получил ни одного "Оскара".

\item Равномерно перераспределить все "Оскары", полученные фильмами одного жанра, между фильмами другого жанра.

\item Представленные операции должны быть реализованы в качестве функций БД, которые необходимо вызывать из уровня бизнес-логики приложения.

\end{itemize}

Особенности хранения объектов, которые должны быть реализованы в системе:


\begin{itemize}[leftmargin=*]

\item Организовать хранение данных об объектах в реляционной СУБД (PostgreSQL). Каждый объект, с которым работает ИС, должен быть сохранен в базе данных.

\item Все требования к полям класса (указанные в виде комментариев к описанию классов) должны быть выполнены на уровне ORM и БД.

\item Для генерации поля id использовать средства базы данных.

\item Для подключения к БД на кафедральном сервере использовать хост pg, имя базы данных - studs, имя пользователя/пароль совпадают с таковыми для подключения к серверу.

\end{itemize}

При создании системы нужно учитывать следующие особенности организации взаимодействия с пользователем:


\begin{itemize}[leftmargin=*]

\item Система должна реагировать на некорректный пользовательский ввод, ограничивая ввод недопустимых значений и информируя пользователей о причине ошибки.

\item Переходы между различными логически обособленными частями системы должны осуществляться с помощью меню.

\item При добавлении/удалении/изменении объекта, он должен автоматически появиться/исчезнуть/измениться на области у всех других клиентов.

\end{itemize}

При разработке ИС должны учитываться следующие требования:


\begin{itemize}[leftmargin=*]

\item В качестве основы для реализации ИС необходимо использовать Jakarta EE, CDI beans.

\item Для создания уровня хранения необходимо использовать JPA + Hibernate.

\item Разные уровни приложения должны быть отделены друг от друга, разные логические части ИС должны находиться в отдельных компонентах.

\end{itemize}

\section*{Как устроено приложение}

В этой работе я сделал каталог фильмов. После входа открывается таблица с полями \texttt{Movie}. Создание и изменение вынесены в диалоговую форму, просмотр по ID — в карточку, удаление — в окно подтверждения. Из таблицы можно перейти к изменению. В карточке показаны и связанные объекты.

Координаты и люди хранятся в справочниках. В форме фильма выбираются существующие записи: один человек может быть режиссёром нескольких фильмов. Новую запись сначала добавляют в справочник. Между разделами можно перейти через меню.

Интерфейс находится в \path{src/main/webapp}: разметка — в \texttt{index.html}, обработка действий — в \texttt{app.js}. Форма собирает данные и отправляет HTTP-запрос. Проверка значений, сохранение и удаление выполняются на сервере.

На сервере запрос сначала попадает в класс из пакета \texttt{web}, затем в сервис и репозиторий. Например, запрос на создание принимает \texttt{MovieResource}. Затем \texttt{MovieService} проверяет данные и связывает фильм с другими объектами, а \texttt{MovieRepository} сохраняет его через \texttt{EntityManager}.

\subsection*{Таблица, поиск и сортировка}

Поиск и сортировка выполняются для всего списка в БД. На клиент приходит только выбранная страница. Поэтому при переходе вперёд порядок не сбивается, а фильтр не ограничивается десятью строками, которые сейчас видны на экране.

Параметры запроса собираются в \texttt{loadMovies} из \texttt{app.js}. В репозитории метод \texttt{page} строит JPQL-запрос: по строкам ищет часть значения без учёта регистра, по числам и дате — точное значение. Пустой фильтр показывает все фильмы, в том числе с незаполненными необязательными полями.

Для сортировки используется \texttt{ORDER BY}. Можно выбрать поле и направление; при одинаковых значениях дополнительно сравниваются ID. Пустые значения идут в конец. Имена полей берутся из списка \texttt{COLUMNS}, поэтому произвольную строку из запроса подставить вместо имени колонки нельзя. Сам алгоритм сортировки выбирает PostgreSQL.

\subsection*{Обновление данных у других пользователей}

Браузер раз в две секунды запрашивает номер общей версии данных. Он хранится в таблице \texttt{app\_revision}. Триггеры из \path{db/001_schema.sql} увеличивают его при изменении фильмов и справочников. Если номер поменялся, \texttt{app.js} заново загружает текущую таблицу и открытую карточку.

Открытую форму редактирования при этом не перезаписываю: введённый текст остаётся, рядом появляется предупреждение. Если другой пользователь удалил фильм, строка исчезнет из таблицы, а в уже открытой карточке останутся последние загруженные данные и сообщение об удалении. Кнопки изменения и удаления в такой карточке отключаются.

\section*{Как данные сохраняются в БД}

Для хранения используются PostgreSQL, JPA и Hibernate. Классы \texttt{Movie}, \texttt{Person}, \texttt{Coordinates} и \texttt{Location} отмечены \texttt{@Entity}. В \texttt{persistence.xml} указан Hibernate и источник данных WildFly. Таблицы создаются SQL-скриптом, а при запуске Hibernate проверяет их соответствие сущностям.

ID создаёт база. Дата добавления задаётся на сервере; в форме её нет. Поле \texttt{creationDate} помечено \texttt{updatable = false}, а триггер БД сохраняет исходную дату при обновлении. Это дата записи в каталоге, а не дата выхода фильма.

Ограничения есть и в Java, и в SQL. Например, название не может состоять из пробелов, бюджет должен быть положительным, а координата Y — не больше 2. Сервис проверяет объект через Bean Validation. Если передать ID несуществующего режиссёра, \path{repository.reference} вернёт ошибку, и фильм не сохранится. Внешние ключи дополнительно защищают связи в самой БД.

Для связей задано \texttt{ON DELETE CASCADE}. Например, удаление человека удаляет фильмы, которые ссылаются на него как на режиссёра, сценариста или оператора. Удаление фильма при этом оставляет общую запись человека в справочнике: она может использоваться в других фильмах.

\subsection*{Транзакции и одновременные изменения}

На сервисах стоит \texttt{@Transactional}. Изменения внутри операции сохраняются вместе. Если при перераспределении наград возникает ошибка, промежуточный результат не должен остаться в БД.

У сущностей есть поле \texttt{version} с \texttt{@Version}. Форма запоминает версию открытого объекта. Перед изменением \path{ValidationService.version} сравнивает её с текущей: если объект успели изменить, сервер отвечает кодом 409. Пользователь должен открыть свежую запись, а не затереть чужие изменения старой формой.

Отдельно используется \texttt{lockWrites}: он блокирует параллельную запись в таблицу фильмов на время транзакции. Такая же блокировка есть у SQL-функции перераспределения наград. Это нужно, чтобы во время подсчёта и переноса «Оскаров» другой запрос не поменял набор фильмов.

\subsection*{Начальные данные}

Каталог заполняется скриптом \path{db/003_demo_data.sql}. В нём есть 12 реальных фильмов и их авторы; ссылки на источники приведены в README. Координаты, рост и обязательные цвета глаз и волос оставлены условными: набор значений в варианте не позволяет точно описать реальных людей. Дата добавления создаётся при записи в БД.

\section*{Специальные операции}

Для них есть отдельный раздел интерфейса. Класс \texttt{SpecialService} проверяет параметры, а \texttt{SpecialRepository} вызывает функции PostgreSQL. Сами функции находятся в \path{db/001_schema.sql}.

\begin{enumerate}
\raggedright
\item \path{delete_one_by_tagline} удаляет один фильм с точным слоганом. Если совпадений несколько, выбирается запись с наименьшим ID.
\item \path{movies_by_tagline} возвращает фильмы, в слогане которых есть заданная подстрока. В этой специальной операции регистр учитывается.
\item \path{movies_genre_less} сравнивает жанры по порядку из задания: ACTION, WESTERN, COMEDY, FANTASY. Для этого используется функция \texttt{genre\_rank}.
\item \path{screenwriters_without_oscars} выбирает сценаристов, у которых есть хотя бы один фильм, но ни у одного фильма нет «Оскара».
\item \path{redistribute_oscars} снимает награды с фильмов жанра-донора и прибавляет их фильмам другого жанра. Награды делятся поровну, остаток распределяется по ID. Например, пять наград между двумя фильмами дадут добавку три и две. Если жанр-получатель пуст, операция отменяется.
\end{enumerate}

Отсутствие наград хранится как \texttt{NULL}: по варианту ненулевое количество должно быть строго больше нуля. Поэтому при перераспределении нельзя просто записать донорам ноль. Оба жанра должны быть заданы и отличаться друг от друга.

\section*{Исходники и запуск}

Код работы: \url{https://github.com/delovoyhomie/movie-lab-53434963}.

Java-код лежит в \path{src/main/java/ru/itmo/movielab}. Интерфейс находится в \path{src/main/webapp}, таблицы и функции БД — в \texttt{db}. Скрипты для Helios — в \path{deploy/helios}; команды запуска и примеры \texttt{curl} приведены в README.

Поэтому адрес с \texttt{127.0.0.1:18081} в браузере ведёт к приложению на сервере. PostgreSQL подключается по адресу \texttt{pg}, база — \texttt{studs}. В серверной сборке имена таблиц и функций имеют префикс \texttt{ml53434963\_}, чтобы не пересекаться с другими работами.

\section*{Выводы}

В работе сделал каталог с созданием, просмотром, изменением и удалением фильмов. Связанные объекты выбираются из справочников, специальные операции выполняются в PostgreSQL. Поиск, сортировка и разбиение на страницы тоже проходят на сервере.

Главное было учесть работу нескольких пользователей: старую форму нельзя сохранить поверх новой записи, а таблицы и карточки должны обновляться после чужих изменений. За это отвечают версии объектов, транзакции и проверка общей версии данных. Вся работа собрана в одно приложение, без отдельного сервера для интерфейса.
